# PR Draft

PR 본문은 **핵심만 간결하게, 꼭 필요한 내용만** 담는다. 리뷰어가 "왜 필요한 변경이고 무엇을 믿을 수 있는지" 판단하는 데 쓰이지 않는 문장은 넣지 않는다.

다음은 어떤 경우에도 본문에 넣지 않는다 — 리뷰어 확인 체크리스트, 코드리뷰 포인트 섹션, 육안/수동 확인 완료 문구, 빌드·검증을 생략한 환경적 사유 서술(미검증 항목은 `[ ]` 체크박스로만 표시), conflict 해결 과정.

## 본문 구성

레포에 `.github/PULL_REQUEST_TEMPLATE.md` 가 있으면 그 헤딩을 쓴다. 없으면 이 골격:

| 섹션 | 담는 것 |
|---|---|
| `## 배경` | 왜 필요한가 — 문제 상태와 근거(수치·커밋 해시·로그). 2-3줄 |
| `## 변경` | 무엇을 바꿨나 — 파일 나열이 아니라 동작 단위 불릿 |
| `## 테스트` | 실제로 실행한 검증만 `[x]`, 안 한 것은 `[ ]` |
| `## 배포 주의사항` | 순서 제약·미검증·범위 밖. 없으면 섹션째로 생략 |

선택 섹션(`영향 범위`, `후속`, `원인`)은 그 내용이 있을 때만 만든다. 빈 섹션을 헤딩만 남겨두지 않는다.

## 꼭 필요한 내용의 기준

**넣는다**
- 판단 근거 — 수치, 커밋 해시, diff 발췌, 로그 대조 표
- **근거의 출처 링크** — 요청·결정이 오간 슬랙 스레드, 지라 티켓, 설계 문서, 선행·후속 PR. "운영 요청", "기획 결정" 처럼 출처를 말로만 적지 않는다. 링크를 모르면 만들기 전에 찾는다 (선행 PR 본문·티켓·슬랙 검색)
- 리뷰어 결정을 바꾸는 트레이드오프, 다른 선택지를 안 택한 이유
- 배포 순서 제약, 미검증 항목, 범위 밖으로 남긴 것

**넣지 않는다**
- 코드가 이미 말하는 것 — 변경 파일 목록, 함수 시그니처, 자명한 동작 설명
- 앞 섹션에서 한 말의 재진술
- 결론으로 이어지지 않는 배경 서술, 일반론

기본 상한은 **전체 15줄, 섹션당 2-3줄**이다. 초과가 필요하면 초과분이 전부 리뷰 판단에 쓰이는 근거(수치·해시·로그)인지 확인하고, 아니면 압축한다. 넣을지 애매하면 뺀다.

## 문체

- `-니다` 체
- 명사형으로 끝나는 항목(체크리스트·불릿)은 온점 없음
- 판단·의견은 방어적 표현 — "적절합니다" → "적절해보입니다"
- 코드·경로·명령은 백틱

## 워크플로우

1. **수집** — `git log origin/main..HEAD`, `git diff origin/main...HEAD --stat`, 브랜치명의 티켓 ID, 레포 PR 템플릿
2. **보강** — 티켓이 있으면 조회해 배경을 채운다. 선행·후속 PR 은 `gh pr list` 나 커밋 메시지에서 찾아 링크
3. **초안 제시** — 제시 전에 15줄 초과·금지 항목 자가점검 후, 제목 + Base/Head + 본문 전문을 보여주고 컨펌받는다 (생성 전 필수)
4. **생성** — 컨펌 후 `gh pr create --title ... --body-file <file>`
5. **CI 확인** — 생성 직후 `check-pr-ci` 스킬로 Actions 상태와 리뷰 코멘트를 확인

제목은 `[TICKET-ID] 무엇을 했는지`. 티켓이 없으면 레포 관례(`fix:`, `chore:`)를 따른다.
본문 끝에 `🤖 Generated with [Claude Code](https://claude.com/claude-code)`.

## 검증 체크박스

실제로 실행한 명령만 `[x]` 로 체크한다. 실행하지 않았거나 실패한 항목은 `[ ]` 로 남긴다. 사유는 배포 판단에 영향이 있을 때만 배포 주의사항에 한 줄로 적고, 환경 사정(로컬 미설치 등)이면 적지 않는다. 통과를 추정해서 체크하지 않는다.

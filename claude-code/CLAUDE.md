## 사용자 컨펌 필수 작업

아래 작업은 실행 전에 반드시 사용자에게 최종 내용을 보여주고 승인을 받은 후 진행한다:

- **PR 생성**: PR 제목과 본문 전체를 보여주고 컨펌 후 `gh pr create` 실행
- **PR 본문 편집**: 변경될 본문 내용을 보여주고 컨펌 후 `gh pr edit` 실행
- **PR 리뷰 코멘트 게시**: 리뷰 내용을 먼저 보여주고 컨펌받거나 pending(draft) 리뷰로만 남긴다. `gh pr review`, `gh api` 등 수단을 불문하고 즉시 공개되는 코멘트 게시는 컨펌 없이 하지 않는다
  - draft 로 남길 때는 **reviews API POST 에서 `event` 를 생략**한다. `event` 를 넣으면 그 즉시 공개 게시되므로 draft 경로에서는 절대 넣지 않는다

    ```bash
    gh api repos/{owner}/{repo}/pulls/{번호}/reviews --method POST --input review.json
    # review.json
    # {"body": "총평", "comments": [{"path": "src/Foo.kt", "line": 42, "side": "RIGHT", "body": "..."}]}
    ```

  - 인라인 코멘트는 `comments` 배열에 한 번에 담는다. pending 리뷰는 사용자·PR 당 하나만 유지되므로 나눠 POST 하면 뒤 요청이 실패할 수 있다
  - 제출은 사용자가 GitHub UI 에서 하는 것이 기본. 컨펌을 받았을 때만 `gh api repos/{owner}/{repo}/pulls/{번호}/reviews/{review_id}/events --method POST -f event=COMMENT` 로 제출한다
  - `/code-review --comment` 는 즉시 게시 경로다. draft 가 목적이면 쓰지 말고 위 reviews API POST 를 쓴다

사용자가 "바로 해줘", "컨펌 없이" 등 명시적으로 생략을 요청한 경우에만 컨펌을 건너뛸 수 있다.

## 커밋 / 푸시 규칙

- **커밋**: 컨펌 없이 바로 진행한다. 커밋 메시지·변경 파일 목록을 사전에 보여주고 승인받을 필요 없음
- **푸시**: 해당 브랜치에 이미 연관된 PR이 있는 경우에만 사전 확인을 받고, 그 외(신규 브랜치 등 PR 없음)에는 바로 푸시한다. 푸시 전 `gh pr list --head <branch>` 로 PR 존재 여부를 확인한다
  - "푸시할까요?"라고 되묻지 않는다 — 커밋 후 PR이 없으면 곧바로 푸시까지 진행한다
- **푸시 후 안내**: 푸시가 끝나면 브랜치 URL과 PR 생성 링크를 함께 알려준다. 관련 지라 티켓이 있으면 티켓 URL도 같이 안내한다

## PR 생성 후 CI 확인

PR을 생성한 후에는 `check-pr-ci` 스킬(`/check-pr-ci`)을 사용하여 GitHub Actions CI 상태와 리뷰 댓글을 확인한다.
사용자가 별도로 요청하지 않아도, PR 생성 직후 CI 결과를 확인할 것을 안내한다.

## 메모리 저장 위치

사용자가 "기억해줘", "남겨놔" 등으로 지시하면 내용의 성격에 따라 저장 위치를 고른다:

- 사용자 전역 선호·작업 정책 → 이 파일 `~/.claude/CLAUDE.md`
- 특정 파일 유형에만 적용되는 규칙 → `~/.claude/rules/*.md` (`paths:` frontmatter 로 스코핑)
- 레포별 컨벤션 → 해당 레포의 `AGENTS.md` / `CLAUDE.md` / `.claude/rules/` / `docs/`
- 재사용 가능한 사실·좌표(URL, 테이블명, 대시보드 ID, 제약) → auto-memory 디렉토리. **기본은 전역 공유 메모리 `~/.claude/memory-shared/`** 이며, 사용자가 프로젝트 한정을 명시했을 때만 `~/.claude/projects/<프로젝트>/memory/` 에 둔다. **단, 안 지켜지면 곤란한 정책은 memory 에 두지 않는다** — 본문은 recall 될 때만 로드되므로 조용히 미적용된다
- 순서·분기가 있는 절차, 도메인 플레이북 → 개인 Skill (`~/.claude/skills/<name>/SKILL.md`). description 만 상시 목록에 오르고 본문은 호출 시 로드된다

프로젝트 스코프 저장은 사용자가 명시적으로 "이 프로젝트에만", "여기서만" 등으로 요청했을 때만 사용한다.

## PR 생성 후 히스토리 재작성 금지

PR이 생성된 이후에는 브랜치를 squash/amend/force-push 해서는 안 된다. 후속 변경은 새 커밋을 쌓아 일반 `git push`로 반영한다.

- PR 생성 전: squash/amend/force-push 자유롭게 사용 가능
- PR 생성 후: 리뷰 코멘트가 특정 커밋/라인 기준으로 달려있으므로, force-push 하면 리뷰 컨텍스트가 outdated 처리되어 흐름이 끊긴다
- 예외: 사용자가 명시적으로 "스쿼시해도 돼", "force-push 해줘"라고 요청한 경우만

## 산출물 분량 기본값

- PR 본문·지라 티켓/댓글·슬랙 메시지·아티팩트·조사 결과 보고 등 **모든 생성 산출물은 첫 초안부터 핵심만 간결하게** 쓴다. 사용자가 "자세히"를 요청한 경우에만 늘린다
- 에이전트 작업 과정 메타정보(yaml diff 확인 완료, 로컬 빌드 생략 사유, conflict 해결 과정)는 산출물에 넣지 않는다. **이 규칙은 PR 본문·티켓·아티팩트 등 완성 산출물에만 적용된다** — 대화 응답에서 검증을 생략한 사유를 밝히는 것은 `rules/code-verification.md` 규칙대로 계속 유지한다. 부가 섹션(코드리뷰 포인트, 리뷰어 체크리스트 등)은 요청이 없으면 만들지 않는다 — PR 본문의 섹션 구성은 `pr-draft` 스킬 규칙이 우선
- 어색한 번역투 단어를 피한다. 교정된 예: 육안(→ 확인), 외삽, 계상(→ 계산). 단, 사용자가 먼저 쓴 어휘(예: 실측)는 그대로 따른다
- 복붙용 슬랙 메시지·답장 초안에 `▎` 같은 인용 바·장식 문자를 넣지 않는다

## 말투 규칙

- PR 본문은 `-니다` 체(존댓말)로 작성 (명사형 항목의 온점 규칙은 프로젝트 CLAUDE.md 참고). 섹션 구성·분량·문체 상세는 `pr-draft` 스킬을 따른다
- 판단이나 의견이 포함된 문장은 방어적 표현 사용 (예: "적절합니다" → "적절해보입니다", "합리적입니다" → "합리적으로 보입니다")

## 사용자 지시·결정 존중

- 사용자가 방식을 명시한 작업(예: full boot 테스트)은 비용·난이도를 이유로 임의 다운그레이드하지 않는다. 대안이 필요하면 **실행 전에** 제안하고 승인받는다
- 사용자가 확정한 설계 결정은 이후 턴에서 임의로 변경·축소하거나 이미 접은 대안을 재제안하지 않는다. 충돌하는 강한 근거를 찾으면 코드를 바꾸지 말고 근거만 1회 보고하고 판단을 기다린다
- 사용자가 지정한 리터럴 값(enum 번호, proto field 번호, 브랜치명, 파일명)은 그대로 사용한다
- 열거 가능한 대상(문서 섹션, 사건 목록, 링크, 모듈 전수)은 임의로 범위를 축소하지 않고 전수 처리한다. 분량상 나눠야 하면 그 사실을 먼저 알린다
- 질문·조사 목적 세션에서는 명시 요청 없이 파일을 수정하지 않는다. 치환 요청은 지시된 리터럴 범위만 바꾸고 주변 로직은 건드리지 않는다
- 기존 문서를 편집할 때 기존 링크·형식·항목을 유실시키지 않는다
- 장기 작업에서는 확정된 결정을 목록으로 유지하고 코드 변경 전에 대조한다

## MCP 서버 등록 시 권한

- 신규 등록 시 read-only 권한만 기본 부여. write 도구는 사용자가 명시 요청한 경우에만 활성화
- endpoint 의 `?toolsets=...` / `?readonly=true` 등 read-only 옵션을 우선 확인하고, 없으면 `permissions.deny` 에 write 계열 도구를 추가해 차단

## Ralph Loop 실행 규칙

- 사용자가 직접 시작한 Ralph Loop 중에는 커밋·push·PR 생성의 per-action 컨펌을 생략하고 자율 실행
- 단, 메인 브랜치 직접 push·force-push·머지 전략(squash/rebase/merge) 결정·예상 밖 파괴적 작업은 여전히 사용자 명시 지시 필요
- Ralph Loop 밖에서는 위 '커밋 / 푸시 규칙'과 '사용자 컨펌 필수 작업'을 그대로 적용
